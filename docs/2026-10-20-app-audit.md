# MEA app audit — October 20, 2026

## Scope and sequence

Special Inventory implementation and focused verification were completed first. The subsequent audit covered the deployed frontend, inventory backend, tracker reference/backend contracts, authentication, local/cloud carts, queues, returns, history corrections, dashboard/activity, service worker, layout, accessibility and release configuration. This is one assistant's source review plus automated and browser fixture checks, not an independent penetration test.

Production source was grounded in repository HEAD `1897021` and the live inventory Apps Script editor. The live script included receipt branding absent from GitHub; its source was backed up outside the publication directory and its branded HTML/plain-text templates were incorporated without changing their Drive image sources.

## Special Inventory behavior

- The live `Special Inventory` tab has seven catalog entries. Classification comes from the source tab and permanent item ID, not the item's category or client-supplied flags.
- Students can choose Borrow/Consume intent and quantity. Checkout separates ordinary transactions from Special Inventory requests even when both have the same intent.
- `submitSpecialRequest` writes `SPECIAL_REQUEST` journal events and a separate visible `Special Requests` projection with `SR` references. It creates no ordinary Borrow/Consume row and sends no email.
- Requests appear in a separate History section with Pending, Verified or Declined status. Existing personal/project/admin history scopes apply.
- Only a school-verified ACCESS Admin can record verification/decline. Revision checks and immutable retry IDs protect decisions. Reviewer, timestamp and notes are retained. Verification records manual handling; it does not automatically create a normal loan, consumption or receipt. Any physical return for these items remains coordinated with SUS.
- The normal order route rejects Special Inventory, protecting stale clients. Already committed old orders retain their normal retry and return behavior.
- Saved/cloud carts preserve special items and authoritative metadata, including when an older draft restores after the live catalog has loaded. There is no migration or historical transaction import. The new projection is created on the first special request.

## Confirmed defects fixed

| Priority | Finding | Resolution and evidence |
|---|---|---|
| High | The offline order worker drained the entire device queue, including other owners and logged-out sessions. | It processes only the active owner, stops on account change, resolves the current verified token when needed, and never persists that token. Regression tests cover other-owner entries, logout, and sign-in upgrades. |
| High | Dashboard/activity snapshots and in-memory state were shared across accounts and backend configurations; denial could fall back to old protected data. | Scoped cache keys, account/session resets, stale-response rejection, authorization eviction, and guarded polling. Tests cover actor/backend separation, denial and late same-actor responses. |
| High | Service worker activation deleted every unrelated cache on the same GitHub Pages origin. Arbitrary same-origin and OAuth callback URLs could also be cached. | Cache namespace includes app scope; only app-shell paths are cached, credential queries are bypassed, cache keys strip ordinary version queries, and legacy caches are retired only when every entry belongs to this app. Regression tests exercise lifecycle, callback exclusion and isolated offline fallback. |
| Medium | Permanent order failures blocked later queued submissions until five retries. | Permanent failures move immediately to the owner's failed bucket; other queued entries proceed. Retry identifiers are preserved. |
| Medium | Local order logging could prevent an online submission if stored JSON was malformed or storage was full. | Best-effort bounded device log; durable offline queue failure still leaves the cart intact. Queue reads validate structure and enqueue deduplicates retry IDs. |
| Medium | Inventory/transaction requests had no deadline and could leave operations waiting indefinitely. | 45-second abort deadlines; dashboard requests have 30-second deadlines. An ambiguous transaction retains its retry key. Timeout history failures may use the explicitly labeled saved snapshot. |
| Medium | Numeric catalog quantities claimed to be available although stock is not decremented by this app. | Labels now say recorded. Special quantities explicitly require SUS verification. No fabricated reservation accounting was added. |
| Medium | Light-theme catalog refresh status and controls lacked contrast. | Use canvas foreground for status text and themed surfaces for refresh controls; special labels use the existing theme foreground. Phone and desktop rendered checks performed. |
| Low | Non-scalar quantities could be coerced to whole numbers, and malformed item entries produced retryable server errors. | Client/server reject boolean/object/array quantities; invalid item entries fail permanently before references or journal writes. |

## Remaining limitations and recommended follow-up

1. **Identity assurance:** existing ID-only inventory submission, own returns and assigned-project history are intentional compatibility behavior, not proof of the person using an ID. Tracker/Dashboard authorization uses an asserted actor ID checked against ACCESS plus an optional shared token; it is not a per-user authenticated session. Treat this as a high-priority security follow-up: require verified school identity for privileged tracker/dashboard reads and writes in a coordinated backend/client migration. This release does not silently replace the user's established ID workflow or claim that hiding controls secures it.
2. **Stock control:** catalog counts are recorded sheet counts. No reservations, automatic depletion, per-item serial tracking or prevention of concurrent physical allocation exists. SUS must confirm availability, especially for special requests. Introducing stock accounting requires a defined baseline and reconciliation policy.
3. **Delivery/projection recovery:** journal commits remain authoritative if visible-sheet projection or email delivery fails. Repairing projections is idempotent, but no automated repair scheduler, email delivery outbox or delivery-status UI exists. Special requests deliberately never email. Ordinary email delivery was mocked in tests; no test receipts were sent to real users.
4. **Scale:** history and reference helpers scan Sheets/journal data repeatedly. There is no pagination, archiving policy or load-test evidence for large event volumes. Current behavior is functional, not a demonstrated high-volume service.
5. **Authentication operations:** the live public Supabase settings returned HTTP 200 with Google and email providers enabled and email autoconfirm disabled. The app keeps `emailReady:false`; SMTP/template readiness and a real new human Google/OTP round trip were not exercised in this audit. No provider secrets or permissions were changed.
6. **Device/platform constraints:** NFC needs supported Android Chrome hardware and was tested through deterministic fixtures, not a physical tag. Browser device emulation is not real iOS/Android hardware. External fonts and the Supabase SDK need network access on first use; school authentication is unavailable offline.
7. **Visual debt:** the mechanical design detector flagged existing small metadata text, aesthetic conventions and some default-theme contrast. Relevant new status/verification contrast was corrected. The established typography and dashboard composition were preserved; the detector output is advisory, not a blanket accessibility certification.

## Rollout and rollback

Update the existing inventory deployment first, preserving URL, execute-as and access settings. Publish the tested frontend next; service-worker release is `mea-app-v36`. No tracker deployment, permission changes, destructive sheet migration or old transaction import is needed.

For rollback, restore the backed-up inventory source and prior deployment version and revert the frontend commit. Retain all new journal events and the Special Requests sheet; rolling back code does not undo legitimate user requests or reviews.
